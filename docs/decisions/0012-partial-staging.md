# ADR 0012: Hunks und Zeilen stagen über `git apply --cached`

- Status: teilweise entschieden. **Entscheidung des Nutzers (2026-11-21, WP-25):** Teile neuer Dateien lassen sich stagen (ohne `git add -N`); Zeilen werden per Klick am linken Rand gewählt, Shift+Klick wählt einen Bereich. **Vorschlag (nicht bestätigt):** die Einzelheiten unten.
- Datum: 2026-11-21

## Kontext

Der Diff kommt seit WP-05 aus `git diff` (ADR 0008), seine Hunks sind also genau die von git. Teile davon lassen sich nur als Patch in den Index bringen: `git add -p` ist interaktiv (Terminal), `git apply` dagegen nimmt einen Patch auf stdin. Was RepoBoard dabei nie darf: ungesicherte Arbeit anfassen (`CLAUDE.md` §2, ADR 0003) – der Worktree ist die Arbeit des Nutzers.

## Entscheidung

- **Nur der Index:** `git apply --cached [--reverse] --whitespace=nowarn [--unidiff-zero] -` über `GitClient.ApplyToIndexAsync`, der Patch auf stdin (`GitRunner` mit `input`, UTF-8 ohne BOM). Immer `--cached`: der Worktree wird nie geschrieben. `--whitespace=nowarn`, weil ein `apply.whitespace=error` des Nutzers sonst eine Zeile ablehnt, die längst in der Datei steht; `--unidiff-zero`, wenn dem Hunk am Anfang oder am Ende Kontext fehlt (`diff.context=0` des Nutzers; sonst heftet git ihn an Anfang bzw. Ende der Datei, Review WP-25).
- **Patch** `HunkPatch.Build` (Core, rein): aus dem gezeigten `DiffHunk` und den gewählten Zeilen. Stagen wendet den Patch vorwärts auf den Index an (die alte Seite des ungestagten Diffs): eine nicht gewählte `-`-Zeile wird Kontext, eine nicht gewählte `+`-Zeile fällt weg. Unstagen wendet ihn rückwärts auf den Index an (die neue Seite des gestagten Diffs): eine nicht gewählte `+`-Zeile wird Kontext, eine nicht gewählte `-`-Zeile fällt weg. Zähler und Anfang im Hunk-Kopf werden neu berechnet (beide Seiten beginnen dort, wo die Seite beginnt, auf die er angewendet wird; eine leere Seite nennt die Zeile davor). CR am Zeilenende und „\ No newline at end of file“ kommen aus den Merkmalen der Zeile. Bekommt eine letzte Zeile ohne Umbruch einen, ist es CR LF, wenn die anderen Zeilen des Hunks auf CR enden.
- **Neue und gelöschte Dateien:** Stagen eines Teils einer neuen Datei ist ein Patch `new file mode` (Modus aus dem Diff-Kopf) gegen `/dev/null` – im Index entsteht die Datei mit genau den gewählten Zeilen, ohne `intent-to-add`. Unstagen eines Teils einer gestagten Löschung ist rückwärts ein Patch `deleted file mode`. Sonst ein Patch auf denselben Pfad; nach einer Umbenennung der neue (nur er steht im Index) – auch für den ganzen Hunk, damit die Umbenennung gestaged bleibt (Review WP-25).
- **Ganze Datei:** Ist die Auswahl jede Änderung der Datei (ein Hunk, alles gewählt, Diff nicht gekürzt), stagt bzw. unstagt RepoBoard die Datei wie das Häkchen – so stimmen Modus, neue und gelöschte Datei ohne Sonderfälle. Nicht beim Unstagen einer Umbenennung (siehe oben). Das Häkchen selbst unstagt eine Umbenennung mit beiden Pfaden, sonst bliebe die Löschung des alten gestaged und der neue wäre ungetrackt (Review WP-25).
- **Abgelehnt, bevor git es sieht:** der abgeschnittene letzte Hunk eines gekürzten Diffs (5 000 Zeilen, ADR 0008); ein Hunk mit U+FFFD (die Datei ist kein UTF-8, der Patch schriebe Ersatzzeichen in den Index); eine Auswahl, nach der eine Zeile ohne Zeilenumbruch nicht die letzte ihrer Seite wäre (eine solche Kontextzeile mit gewählten Zeilen danach wird als `-`/`+` mit Zeilenumbruch geschrieben – „a“ ohne Umbruch, „+b“ gewählt ergibt „a\nb“; was dann noch übrig bleibt, wird abgelehnt); symbolische Links und Submodule (`120000`, `160000`) sowie ein Diff aus gelöschter und neuer Datei (Typwechsel, von `-M` nicht gepaarte Umbenennung) – nur als Ganzes, je mit eigener Meldung.
- **Veralteter Diff und Diff-Treiber (Review WP-25):** Im Tor des Repos liest `BoardService.StageHunkAsync` den Diff neu. Ist er nicht mehr der gezeigte, wird nichts gestaged (auch nicht die ganze Datei, die sonst eine ungesehene Änderung mitnähme) – Meldung, der neue Status bringt den neuen Diff. Für einen Patch liest es ihn zusätzlich mit `--no-textconv`: weicht der vom gezeigten ab, zeigt ein Diff-Treiber die Datei, und Teil-Stagen wird abgelehnt – sonst käme der Text des Treibers als Datei in den Index (bei einer neuen Datei prüft git nichts dagegen; mit git-crypt wäre das ein Geheimnis im Klartext). Die ganze Datei geht weiter (`git add`). Zwischen diesem Lesen und `git apply` prüft git jede Kontextzeile gegen den Index und wendet alles oder nichts an.
- **Auswahl in der UI** (`UI/State/LineSelection`): Klick auf den Rand (Nummern und Vorzeichen) wählt eine geänderte Zeile oder hebt sie auf, Shift+Klick wählt alle geänderten Zeilen vom letzten Klick bis hier; immer nur in einem Hunk. Der Knopf am Hunk-Kopf heißt dann „Zeilen stagen (n)“. Die Auswahl bleibt bei einem neuen Status, solange ihr Hunk gleich aussieht.

## Folgen

- Kein neues Werkzeug, keine eigene Patch-Logik außer dem Bau des Patches: Anwenden, Prüfen und Atomarität macht git.
- `git apply` startet keine Hooks; `--literal-pathspecs` ist nicht nötig, der Pfad steht im Patch (mit C-Quoting bei `"`, `\` und Steuerzeichen).
- Auswahl per Ziehen und Tastatur fehlen (Backlog).
